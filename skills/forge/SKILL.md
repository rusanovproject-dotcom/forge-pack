# /forge — Кузница: единый цикл разработки

Цель: любая задача по коду или проектированию проходит через **осознанный качественный цикл**,
а не «накидал кода» / «накидал агентов наугад». Партнёр остаётся в цикле и видит, что и почём.

Принцип: **скилл = мозг и партитура** (живёт в твоём контексте), **субагенты = руки**
(изолированная/параллельная работа). Не плодить движки без нужды — вес задачи решает глубину.

---

## Шаг −1 — Preflight окружения (первый раз в сессии, дёшево)

Forge опирается на внешние компоненты. Прежде чем обещать цикл — убедись, что они есть.
Молчаливое допущение «всё настроено» — главный источник тихой деградации (цикл делает вид,
что прошёл ревью, а ревьюеров не спавнил).

- **Плагины.** Трек A/B зовут `superpowers:*` и `compound-engineering:*` по имени. Не резолвятся
  (Skill/Agent кидает «not found») → **СТОП, не имитируй цикл руками**. Скажи прямо: «нужен плагин
  X — поставь `/plugin marketplace add … && /plugin install …`». Не соскальзывай в псевдо-цикл.
- **Тул `Workflow`.** На нём держится весь Трек B (рой). Нет тула → Трек B недоступен,
  честно предложи Трек A вместо роя (как с `/goal` ниже).
- **Трек C** (автономный loop) держится на нативном `/goal`. Нет его в твоей версии → фолбэк
  на Трек A (TDD-зелёный как критерий), не падай.

Проверка дешёвая и разовая: если компонент только что отработал — не перепроверяй каждый шаг.

## Шаг 0 — Классификатор + фильтр (ВСЕГДА первым)

Перед любым действием определи **вес** задачи. Это главный фильтр — он экономит токены и время.

| Вес | Что это | Куда |
|-----|---------|------|
| **тривиально** | одна строка, опечатка, правка текста/конфига, переименование, 1 файл <50 строк | **просто Edit. СТОП.** Без цикла, без ревьюеров |
| **одна голова (лёгкий)** | фича / багфикс / рефактор обозримого размера, понятная зона | **Трек A — лёгкий путь** (TDD + correctness/maintainability + verify) |
| **крупная фича** | новая подсистема, незнакомая зона, несколько модулей, развилки | **Трек A — полный путь** (ce-plan → executing-plans → TDD → ревью → verify) |
| **рой** | объём не лезет в одну голову · нужно много углов разом · нужна уверенность через проверку | **Трек B — Рой** |
| **автономный loop** | задача под измеримую метрику ИЛИ мягкое «лучше/хуже», крутить до критерия | **Трек C — Автономный loop** (`/goal`, опционально) |

**⚠️ Risk-override (бьёт классификацию по размеру).** Задача НИКОГДА не «тривиально» и не
срезается до лёгкого пути, если трогает: **auth / права / деньги / мутацию данных / миграцию /
публичный эндпоинт / деплой / секреты**. Опасные диффы обычно маленькие — классифицируй по РИСКУ,
не по числу строк. Такое = минимум одна голова + обязательный `security-reviewer` (+`adversarial` если деньги/auth).

Веса комбинируются: например, рой (Трек B) может писать код по методологии Трека A внутри своих
агентов; автономный цикл (Трек C) исполняется через тот же код-цикл A на каждой итерации.

**Фильтр роя (СТОП перед Workflow).** Рой = десятки агентов = жжёт токены. Оправдан только если:
1. объём не лезет в одну голову (аудит/миграция всей кодбазы, десятки файлов);
2. нужно много углов разом (ревью с N сторон, сравнение N подходов);
3. нужна уверенность через проверку (найти → скептики опровергают → выжившие).

Ни один не подходит → **не рой**. Скажи прямо: «тут хватит одной головы / прямого ответа».

## Трек A — Code cycle (Superpowers + Compound)

Детерминированный путь кода. Детали и полная матрица ревью — `references/code-cycle.md`.
**Два пути по весу** (см. Шаг 0): лёгкий не должен быть дороже соблазна обойти forge руками.

**Фаза 0 — Recon стека (всегда, дёшево).** Определи как тут запускаются тесты/линт/билд
(`package.json` / `pyproject.toml` / `go.mod` / Makefile), фреймворк, конвенции. Убедись, что тесты
ИДУТ до старта. Незнакомый/большой репо → `compound-engineering:research:repo-research-analyst`.
Без этого TDD «падающий тест» — пустая аспирация.

**Лёгкий путь (одна голова):** Фаза 0 recon → **TDD** (`superpowers:test-driven-development`) →
ревью `correctness` + `maintainability` (+ `security` если risk-override) → docrutка →
`superpowers:verification-before-completion` → land. Без ce-plan/executing-plans — не дави трением.

> **⛔ Reviewer Gate (бьёт по соблазну схлопнуть в линию).** Ревью — это **спавн отдельных
> субагентов** (`Agent` tool, `subagent_type: compound-engineering:review:*`, в ОДНОМ сообщении
> параллельно). Их ценность = **чистый контекст**: они видят код незамыленным взглядом. Сам себя в
> текущей сессии ты проверить НЕ можешь — это самопроверка тем же контекстом, не ревью. «Готово»
> запрещено, пока ты реально не вызвал ревьюеров-субагентов и не свёл их фидбек. Лень/«и так понятно» —
> не основание срезать. Единственное исключение — вес «тривиально» (там ревью вообще не нужно).

**Полный путь (крупная фича):** добавляет к лёгкому:
1. **План** — размыто → `compound-engineering:ce-brainstorm`; ясно → `compound-engineering:ce-plan`.
   Важный план → `compound-engineering:document-review` ПЕРЕД кодом.
2. **Исполнение** — `superpowers:executing-plans` (чекпоинты ревью по ходу).
3. **Дебаг** — любой баг/упавший тест → `superpowers:systematic-debugging` ДО любого фикса.
   **Verify падает 2 раза подряд → СТОП, `/rewind` к точке + иной подход**, не долбить корректировками
   (последовательные «поправь ещё раз» работают хуже отката к развилке).

**Фаза 6 — Land (приземление).** Готовый код не висит дифом: на main → сперва ветка; понятный коммит;
**Draft PR** и дождись ревью/аппрува перед мержем в `main` — не пушить и не мержить в main напрямую.
Если у тебя настроен pre-push хук (проверка секретов/ПД) — дай ему отработать. Это шаг «ship», ради
которого цикл и затевался. *(Гейт PR/аппрува — твоя конвенция; forge её уважает, но не навязывает свою.)*

**Матрица ревью (кого звать), все `compound-engineering:review:*`, в одном сообщении:**
всегда `correctness-reviewer` + `maintainability-reviewer`;
auth/ввод/права → `security-reviewer`; БД/циклы/кэш/I/O → `performance-reviewer`;
retry/таймауты/джобы → `reliability-reviewer`; миграции/схема → `data-migrations-reviewer`;
API/типы → `api-contract-reviewer`; стек → `kieran-typescript-reviewer` / `kieran-python-reviewer` / `dhh-rails-reviewer`;
слабые тесты → `testing-reviewer`; **диф ≥50 строк ИЛИ деньги/auth/мутация данных → +`adversarial-reviewer`**.

## Трек B — Рой (поглощённый дирижёр)

Когда Шаг 0 дал «рой». Полное ремесло — `references/swarm.md` (5 типов · 4 паттерна ·
правила мастерства · страховка от runaway · грабли рантайма). Кратко:

- **Классифицируй:** understand / design / review / research / migrate.
- **Паттерн:** pipeline (по умолчанию) · parallel (барьер, только при кросс-зависимости) ·
  adversarial verify · loop-until-dry.
- **Покажи план роя + цену ПЕРЕД запуском**, жди «го».
- **Один Workflow = одна фаза-веер.** Несколько подряд > один монстр.
- **Ремесло:** не давай LLM работу кода · дешёвая модель на разведку · `schema` на каждом
  агенте по пайплайну · сначала узкий срез → масштаб · корректность > скорости.

## Трек C — Автономный loop (опционально)

Когда задача итеративная под критерий («крути, пока не станет лучше / пока метрика не сойдётся»).
В этот пак входят Треки A и B — их достаточно для 90% работы. Трек C держится на **нативном `/goal`**
(если он есть в твоей версии Claude Code — проверь; после каждого хода маленькая модель судит
«выполнено / нет»):

- **Есть `/goal`** → поставь completion-condition, дай крутить автономно до критерия.
- **Нет `/goal`** → простой автоном собери руками через Трек A (TDD-зелёный как критерий) или гоняй
  итерации сам, сверяясь с рубрикой готовности каждый раунд.

> Продвинутый Трек C (проектировщик цикла с типизированной рубрикой, cross-model council, budget-guards)
> живёт в отдельном скилле и в этот пак не входит — здесь он намеренно упрощён до `/goal` + фолбэк,
> чтобы не тащить лишние зависимости. Начни с A/B, к автономным циклам вернёшься, когда упрёшься в них.

## Сквозное правило — принципы ВНУТРЬ исполнителей

Чтобы исполнитель (хоть одна голова, хоть рой) действовал по методологии, а не «тупо».
**Принцип маппится на РОЛЬ агента, не «всем TDD»** (TDD нужен только тем, кто пишет код):

| Роль агента в рое | Что прошить |
|-------------------|-------------|
| пишет код (migrate, code-фаза) | в промпт первой строкой: *«Сначала Skill: superpowers:test-driven-development, следуй; затем — задача…»* |
| ревьюер | `agentType: 'compound-engineering:review:<persona>'` (готовый system-prompt-судья) |
| understand / research / design (не пишет код) | **никакого TDD** — это мусор для них; дай чёткую рубрику задачи в промпт |

- **main loop** (ты) → вызывай скиллы Superpowers/Compound напрямую.
- **Проверяй следование, не верь на слово:** у код-агента в `schema` поле-маркер
  (напр. `tdd_done: "red→green"` / `followed_skill: "..."`); пусто → реджект/переспрос.
  Top-level Workflow-агент видит Skill+ToolSearch и реально грузит скилл — методологию прошить можно.
  Но на масштабе параллельных агентов следование держи маркером в schema, а не презумпцией.

Ограничение рантайма остаётся: **вложенность одна** — агент роя НЕ спавнит суб-суб-агента.
Скилл вызвать может, под-рой развернуть — нет. Вся веерная оркестрация — на верхнем уровне скрипта.

## Экономия и guardrails (железно)

1. **Preflight первым** — не обещай цикл, не убедившись, что плагины/тулы на месте (Шаг −1).
2. **Вес решает глубину.** Тривиально → Edit. Не гнать 6 ревьюеров на кнопку, не звать рой на воробья.
3. **Фильтр роя обязателен** — три случая, иначе одна голова.
4. **Страховка от runaway** — на незнакомом рое держи `/workflows` открытым, читай скрипт глазами,
   помни кап (16 одновременно / 1000 за прогон). Degenerate loop выжигает лимит за минуты.
5. **Не молчи про обрезку** — ограничил охват (топ-N, без ретраев, сэмпл) → скажи явно.
6. **Секреты наружу — только осознанно** — если цикл шлёт код во внешний сервис/модель, вырежь
   секреты (`.env`, `secrets/**`, `*.key`) и получи согласие владельца.
7. **Ревью ≠ самопроверка (Reviewer Gate).** Любой не-тривиальный код-цикл закрывается только
   спавном ревьюеров-субагентов в чистом контексте. Проверил «сам в этой же сессии» = ревью НЕ
   состоялось. «Готово» = TDD-зелёный **+** свёл фидбек реальных субагентов **+** verification.

## Что вернуть в конце

1. Результат (диф / отчёт / карта).
2. Что реально покрыли vs что обрезали.
3. Прошла ли верификация (для кода) — «готово» только после неё.
4. Следующий логичный шаг.

Без воды. Кузница куёт, но партитуру читает партнёр.
