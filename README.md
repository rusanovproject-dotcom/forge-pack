# Forge — Кузница: единый цикл разработки для Claude Code

**Один вход для любой задачи по коду.** Вместо «накидал кода наугад» Forge ведёт
работу по осознанному циклу: определяет вес задачи → план → код через TDD →
ревью отдельными агентами с чистым контекстом → верификация. И сам решает,
*насколько глубоко* копать: опечатку не раздувает до процесса, крупную фичу гонит
по полному пути, объёмную работу раскидывает роем.

Главное правило, ради которого всё затевалось: **ревью — это не самопроверка.**
Слово «готово» разрешено только после того, как код реально прошёл через
отдельных ревьюеров-субагентов и верификацию, а не после «ну вроде норм».

> **Пак самодостаточен.** Всё, что зовёт `/forge`, лежит внутри этого
> репозитория: скиллы, плагины, агенты-ревьюеры. Ставится одной командой, ничего
> не докачивает, битых ссылок нет — и это [проверяется машинно](#проверка-целостности),
> а не обещается на словах.

---

## Быстрый старт

```bash
git clone https://github.com/rusanovproject-dotcom/forge-pack.git
cd forge-pack
./install.sh
```

Перезапусти Claude Code и проверь:

```
/forge собери мне маленькую фичу
```

Установщик кладёт скиллы `forge` и `looper` в `~/.claude/skills/`, подключает
репозиторий как маркетплейс и ставит из него два плагина-зависимости. Если
настоящие `superpowers` или `compound-engineering` у тебя уже стоят из апстрима —
вендоренные копии не ставятся, апстрим свежее. Повторный запуск безопасен:
прежние версии уносятся в бэкап с отметкой времени.

Единственное требование — установленный Claude Code с CLI `claude`.

## Как это работает одним взглядом

```
любая задача по коду
        │
   Шаг −1: живы ли зависимости? ── нет → честно сказать, чего не хватает
        │                              (и не имитировать цикл руками)
   Шаг 0: какой ВЕС?
        ├─ тривиально ───────────→ просто Edit. Стоп. Никакого цикла
        ├─ одна голова ──────────→ Трек A лёгкий: recon → TDD → 2 ревьюера → verify
        ├─ крупная фича ─────────→ Трек A полный: + план + ревью плана
        ├─ рой ──────────────────→ Трек B: план и цена → «го» → веер агентов
        └─ автономный loop ──────→ Трек C: крутить до критерия
        │
   поверх всего: risk-override
   auth · деньги · данные · миграция · деплой · секреты
        └─→ никогда не «тривиально», всегда + security-reviewer
```

## Логика методологии (коротко)

Полностью — в [docs/METHODOLOGY.md](docs/METHODOLOGY.md). Шесть принципов, на
которых стоит пак:

**1. Вес задачи решает глубину.** Процесс, одинаково дорогой для опечатки и для
новой подсистемы, не соблюдается никогда. Поэтому лёгкий путь сделан дешевле
соблазна обойти цикл руками, а тривиальное вообще выходит из цикла на первом шаге.

**2. Риск бьёт размер.** Опасные диффы обычно маленькие: три символа в проверке
прав ломают авторизацию целиком. Всё, что трогает auth, деньги, данные, миграции,
деплой или секреты, классифицируется по риску, а не по числу строк.

**3. Ревью делается чужим контекстом.** Ценность ревьюера не в том, что он умнее,
а в том, что он не видел, как код писался. Автор в той же сессии смотрит на код
сквозь свой замысел и потому проверить себя физически не может. Ревью = спавн
отдельных субагентов, параллельно, в одном сообщении.

**4. Сначала тест, потом код.** Тест, написанный после кода, наследует допущения
автора и зелёный всегда. Тест, написанный до, обязан сначала упасть — падение
доказывает, что он вообще что-то проверяет.

**5. Рой нужно оправдать.** Веер из десятков агентов жжёт токены. Оправдан ровно
три случая: объём не лезет в одну голову, нужно много углов разом, нужна
уверенность через опровержение. Иначе — одна голова, и сказать это прямо.

**6. Человек в цикле.** Цена роя показывается до запуска. Мерж в основную ветку —
с явной отмашки. Обрезал охват — скажи вслух, молчаливая обрезка читается как
«покрыли всё».

## Что внутри и почему именно это

```
forge-pack/
├── skills/
│   ├── forge/                    → ~/.claude/skills/forge   ·  зовётся /forge
│   │   ├── SKILL.md                 классификатор веса + развилка на треки
│   │   └── references/
│   │       ├── code-cycle.md        Трек A — код-цикл и матрица ревью
│   │       ├── swarm.md             Трек B — рой: паттерны, страховка от runaway
│   │       └── loop-design.md       Трек C — автономный loop
│   └── looper/                   → ~/.claude/skills/looper  ·  зовётся /looper
│                                    проектировщик цикла для Трека C
├── plugins/
│   ├── superpowers/              → плагин  ·  superpowers:*
│   │                                процесс: TDD, дебаг, исполнение, верификация
│   └── compound-engineering/     → плагин  ·  compound-engineering:*
│                                    план и ревью: 3 скилла + 33 агента-ревьюера
├── docs/
│   ├── METHODOLOGY.md               логика цикла целиком
│   ├── MAP.md                       карта: каждый скилл и агент, кто его зовёт
│   └── VENDORING.md                 провенанс: чей код, версии, лицензии, правки
├── scripts/
│   ├── build-vendor.sh              пересборка вендоринга из апстримов
│   ├── depersonalize.py             снятие личного со скилла forge
│   └── check-links.py               доказательство самодостаточности
└── install.sh
```

**Почему две библиотеки, а не одна.** Они не дублируются, и в паке это соблюдается
строго. **Superpowers** (Jesse Vincent) — процесс: как исполнять, тестировать,
дебажить, доказывать завершённость. **Compound Engineering** (Every) — план и
ревью: как разложить задачу до кода и кто её потом проверит. На каждой фазе
зовётся одна конкретная вещь, а не всё подряд — иначе лёгкий путь перестал бы
быть лёгким.

**Почему superpowers взят целиком, а compound-engineering — подмножеством.**
Скиллы superpowers ссылаются друг на друга: замыкание от четырёх нужных даёт
девять, а до всех четырнадцати — полторы сотни килобайт разницы. Дешевле взять
целиком, чем однажды не заметить ссылку. У compound-engineering наоборот: 41
скилл, из них к циклу разработки относятся три, остальное — Figma, картинки,
Rails, Slack. Взято точное транзитивное замыкание и ни байтом больше.

Кто именно из 33 агентов когда зовётся — таблица в [docs/MAP.md](docs/MAP.md).

## Под какие задачи (и когда НЕ надо)

| Задача | Что сделает Forge |
|---|---|
| «поправь опечатку», «переименуй» | ничего лишнего — просто Edit, без цикла |
| «сделай вот эту фичу» | recon стека → TDD → correctness + maintainability → верификация |
| «крупная незнакомая подсистема» | плюс план (`ce-plan`) и ревью плана до кода |
| «трогает auth / деньги / данные» | risk-override: обязательный security, на деньгах ещё adversarial |
| «разбери весь проект», «сравни 5 подходов» | рой агентов с планом и ценой перед запуском |
| «крути, пока метрика не сойдётся» | автономный loop под измеримый критерий |

**Не для Forge:** ответ на вопрос, вызов одного конкретного субагента, правка
одной строки. В этих случаях Forge сам скажет, что цикл не нужен, и не станет
разводить процесс.

## Роутинг: чтобы Claude заходил сам

Скилл срабатывает явно — `/forge собери фичу X` — или по триггерам вроде «напиши
код», «построй сервис», «реализуй», «прогони по циклу», «запусти рой».

Чтобы Claude вспоминал про цикл без напоминаний, добавь в свой `CLAUDE.md`:

```markdown
## Разработка → через Forge

Любая задача по коду (фича, сервис, фронт/бэкенд, фикс, миграция) и любая
многоагентная оркестрация идут через скилл `/forge`, а не «накидал кода руками».
Forge сам определит вес: тривиальная правка → просто Edit без цикла; фича →
код-цикл (TDD + ревью субагентами); объём или много углов → рой агентов;
итерация под критерий → автономный loop.

НЕ через forge: «позови [агента]» (один субагент), ответ на вопрос, правка одной
строки или текста.
```

## Проверка целостности

Обещание «внутри есть всё» без проверки — просто надежда. Поэтому оно
проверяется машинно:

```bash
python3 scripts/check-links.py
```

Скрипт обходит весь репозиторий и требует, чтобы **каждая** ссылка вида
`superpowers:X` и `compound-engineering:Y:Z` резолвилась в реально существующий
файл внутри пака. Заодно ловит битые симлинки, пустые файлы и скиллы без
frontmatter. Он же встроен в конец `build-vendor.sh`, поэтому пак не может
собраться с висячей ссылкой незаметно.

Манифесты проверяются штатным валидатором:

```bash
claude plugin validate .                          # маркетплейс
claude plugin validate plugins/superpowers --strict
claude plugin validate plugins/compound-engineering --strict
```

## Обновление вендоринга

Вендоринг собирается скриптом, не руками:

```bash
./scripts/build-vendor.sh
```

Скрипт берёт апстримы с локальной машины, пересобирает дерево, снимает со скилла
`forge` всё личное и сразу прогоняет проверку ссылок. Если апстрим изменился так,
что таблица замен больше не совпадает, сборка **падает с ошибкой** и показывает,
какая строка не нашлась. Это сделано нарочно: молча пропущенная замена означала
бы, что в публичный репозиторий уехало личное.

| Компонент | Автор | Апстрим | Лицензия |
|---|---|---|---|

Содержание вендоренных файлов не переписано: пространства имён сохранены
байт-в-байт, поэтому `/forge` едет в пак ровно тем файлом, который работает у
автора. Точный список изменений (два удаления в superpowers, ноль правок
содержания) — в [docs/VENDORING.md](docs/VENDORING.md).

Хочешь получать обновления библиотек — ставь их из апстрима напрямую, установщик
это учитывает и вендоренные копии тогда не трогает.
