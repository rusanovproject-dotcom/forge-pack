# Карта пака: что здесь лежит и зачем каждая штука

Справочник. Для каждого скилла и агента — откуда он, кто его зовёт и почему он
вообще попал в пак. Если хочешь взять из пака что-то по частям, смотри сюда.

Общая логика простая: **`/forge` ничего не делает сам**. Он классифицирует задачу
и зовёт нужный инструмент. Всё, что он может позвать, обязано лежать внутри
репозитория — иначе цикл делает вид, что прошёл, а на деле не прошёл.

---

## Верхний уровень

| Что | Куда ставится | Как зовётся | Роль |
|---|---|---|---|
| `skills/forge` | `~/.claude/skills/forge` | `/forge` | Дирижёр. Классифицирует вес задачи и выбирает трек |
| `skills/looper` | `~/.claude/skills/looper` | `/looper` | Проектировщик автономного цикла (Трек C) |
| `plugins/superpowers` | плагин Claude Code | `superpowers:*` | Процесс: как делать |
| `plugins/compound-engineering` | плагин Claude Code | `compound-engineering:*` | План и ревью: что делать и кто проверит |

Разделение между двумя библиотеками неслучайное и в паке соблюдается строго:
**Superpowers отвечает за процесс** (TDD, дебаг, верификация), **Compound
Engineering — за план и ревью**. Они не дублируют друг друга, поэтому в цикле
зовётся не «всё подряд», а конкретный инструмент под конкретную фазу.

## skills/forge — сам дирижёр

| Файл | Что внутри |
|---|---|
| `SKILL.md` | Шаг −1 preflight → Шаг 0 классификатор веса → развилка на три трека → guardrails |
| `references/code-cycle.md` | Трек A: код-цикл целиком, фазы 0–6, полная матрица ревью |
| `references/swarm.md` | Трек B: рой агентов — 5 типов задач, 4 паттерна, страховка от runaway |
| `references/loop-design.md` | Трек C: автономный loop — движки, проектировщик, guardrails |

Файлы `references/` подгружаются только когда трек реально выбран. Поэтому
`/forge` дёшев на входе: в контекст сначала попадает только классификатор.

## plugins/superpowers — процесс (14 скиллов)

Плагин взят целиком. Прямо из `/forge` зовутся четыре, остальные подтягиваются
по ссылкам изнутри самих скиллов либо полезны сами по себе.

### Зовутся из `/forge` напрямую

| Скилл | Когда срабатывает | Зачем в паке |
|---|---|---|
| `test-driven-development` | перед написанием любого кода | Ядро Трека A. Сначала падающий тест, потом код — без исключений для фич и багфиксов |
| `systematic-debugging` | любой баг или упавший тест | Гипотеза → проверка → вывод **до** фикса. Запрещает гадать наугад |
| `verification-before-completion` | перед словом «готово» | Требует прогнать команды и показать вывод. Без него «готово» — это мнение, а не факт |
| `executing-plans` | есть написанный план | Ведёт план с чекпоинтами ревью, чтобы он не рассыпался на середине |

### Подтягиваются по ссылкам из четырёх выше

| Скилл | Кто ссылается | Зачем |
|---|---|---|
| `writing-plans` | executing-plans, subagent-driven-development | Формат плана, который потом исполняется |
| `subagent-driven-development` | executing-plans, writing-plans | Исполнение независимых задач плана в текущей сессии |
| `using-git-worktrees` | executing-plans, writing-plans, subagent-driven | Изоляция работы, когда агенты правят файлы параллельно |
| `finishing-a-development-branch` | executing-plans, subagent-driven | Как приземлить ветку: мерж, PR, что с ней делать |
| `requesting-code-review` | subagent-driven-development | Как правильно попросить ревью, чтобы оно было предметным |

### Взяты «за компанию» — плагин целиком

| Скилл | Зачем может пригодиться |
|---|---|
| `brainstorming` | Разведка требований до кода. Пересекается с `ce-brainstorm`, но заходит с другой стороны |
| `receiving-code-review` | Как читать фидбек ревьюеров и не спорить с ним рефлекторно |
| `dispatching-parallel-agents` | Ручной запуск параллельных агентов, когда рой избыточен |
| `using-superpowers` | Мета-скилл: приучает вообще проверять наличие подходящего скилла |
| `writing-skills` | Если решишь писать свои скиллы поверх пака |

**Почему целиком, а не четыре нужных.** Скиллы ссылаются друг на друга.
Транзитивное замыкание от четырёх даёт девять, разница до четырнадцати —
полторы сотни килобайт текста. Взять целиком дешевле, чем однажды не заметить
ссылку и получить битый цикл.

## plugins/compound-engineering — план и ревью

### Скиллы (3 из 41)

| Скилл | Когда | Зачем в паке |
|---|---|---|
| `ce-plan` | крупная фича, полный путь Трека A | Разбивает задачу на исполнимые единицы до кода. Плохой план дешевле плохой реализации |
| `ce-brainstorm` | задача ещё размыта | Когда планировать нечего — сначала надо понять, что вообще делаем |
| `document-review` | важный план перед кодом | Ревью самого плана семью персонами. Ловит дыру в замысле, пока она стоит один абзац, а не неделю работы |

к циклу разработки отношения не имеют и в пак не взяты.

### Агенты-ревьюеры кода (19) — сердце Трека A

Матрица ревью в `/forge` устроена так: два ревьюера зовутся **всегда**,
остальные — по зоне диффа. Все они спавнятся параллельно, одним сообщением,
каждый в **чистом контексте**.

| Агент | Когда зовётся |

| `review:testing-reviewer` | **всегда** — дыры в покрытии, слабые ассерты, хрупкие тесты |
| `review:security-reviewer` | auth, публичные эндпоинты, пользовательский ввод, права |
| `review:performance-reviewer` | запросы к БД, тяжёлые циклы, кэш, интенсивный I/O |
| `review:reliability-reviewer` | ретраи, таймауты, фоновые джобы, обработка ошибок |
| `review:data-migrations-reviewer` | миграции, изменения схемы, бэкфилы |
| `review:api-contract-reviewer` | роуты API, типы запроса/ответа, сигнатуры |

| `review:kieran-python-reviewer` | код на Python |
| `review:dhh-rails-reviewer` | код на Rails |
| `review:adversarial-reviewer` | **дифф ≥50 строк ИЛИ деньги/auth/мутация данных** — строит сценарии поломки, а не сверяется с чек-листом |
| `review:architecture-strategist` | зовётся из `ce-plan` — соответствие архитектуре |
| `review:security-sentinel` | зовётся из `ce-plan` — аудит безопасности |

### Агенты ревью документов (7) — для `document-review`

`coherence` · `feasibility` · `scope-guardian` · `security-lens` · `product-lens`
· `design-lens` · `adversarial-document`.

Проверяют не код, а замысел: противоречия между разделами, выживет ли подход при
встрече с реальностью, не раздут ли объём, что с безопасностью на уровне плана.

## skills/looper — Трек C

Проектировщик автономного цикла. Не исполняет сам: интервьюирует, критикует по
рубрикам и эмитит `loop.yaml` → `LOOP.md` + `RUN_IN_SESSION.md` + `run-loop.py`.

Нужен, только когда критерий «готово» мягкий («лучше/хуже») или цикл длинный и
важный. Если у задачи есть тесты — рубрика уже есть, это тесты, и `/looper` не
нужен. Такое правило зашито в сам `/forge`, чтобы не разводить проектирование
там, где хватит зелёных тестов.

## Чего в паке нет

| Что | Почему |
|---|---|
| `/autoresearch` | У апстрима нет файла лицензии. Чужой код без лицензии в публичный репозиторий класть нельзя. Ставится отдельно, если нужен |
| `/goal` | Нативная команда Claude Code — вендорить нечего. `/forge` проверяет её наличие и честно откатывается |
| инструмент `Workflow` | Часть среды Claude Code, не скилл. Нет его — Трек B недоступен, `/forge` предложит Трек A вместо роя |

Подробности по каждому вендоренному куску — версии, коммиты, лицензии,
внесённые изменения — в [VENDORING.md](VENDORING.md).
